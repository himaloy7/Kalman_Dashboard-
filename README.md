Compute Topology Note: The deployed GRU runs on CPU deliberately. At ~2,000 parameters, the workload has insufficient SIMT parallelism to amortize host-to-device transfer overhead, and per-request inference latency on CPU is already sub-millisecond. This mirrors the eventual RFSoC deployment, where the same rationale drives mapping to PL fabric rather than a GPU co-processor. GPU execution is validated separately in the offline baseline (beam_tracker.py), where CUDA serves as a reference path ahead of HLS synthesis.

Live RFSoC Integration Path: The /api/kalman-step endpoint accepts LOS/RIS geometry as a JSON payload, so an RFSoC-side UDP forwarder can replace the scene simulator without modifying the backend. Feeding real measurements from an RFSoC-class device — for example, the XCZU48DR testbed — into this pipeline would let the dashboard serve as a live diagnostic for the scenarios in Kokkoniemi et al.: LOS vs. RIS SNR decomposition under 140 GHz propagation, Kalman gain behavior as the filter absorbs bistatic-RIS path loss (n = 4 for equidistant geometry, converging to n = 2 as the RIS approaches either endpoint), and GRU blockage predictions evaluated against measured obstructions in a 10–100 m SCBS deployment. The output panels would show whether the EKF's adaptive R_k logic correctly tracks the paper's 5–12 dB noise figure regime, and whether the GRU transfers from its synthetic training distribution to empirical sub-THz measurements. This is the deployment-validation step that converts a behavioral baseline into a hardware-anchored result.
